# Проектный практикум · Команда 13

Прогнозирование почасового спроса на аренду велосипедов в Сеуле
(датасет Seoul Bike Sharing, 8 760 почасовых наблюдений за один год).

## Постановка задачи и исследовательский анализ

### Задача

- **Целевая переменная:** `Rented Bike Count` — число аренд за час.
- **Тип задачи:** регрессия (прогноз вещественного числа).
- **Объект данных:** один час наблюдения (каждая строка = один час
  работы сервиса с привязанными погодными и временными признаками).

### Исследовательский анализ

Полный EDA выполнен в [`notebooks/eda.ipynb`](notebooks/eda.ipynb).
Краткие выводы:

- **Качество данных.** Пропусков и дубликатов нет; почасовая сетка полная
  (каждый час периода представлен ровно один раз). Подозрительные значения:
  17 нулевых значений влажности (возможная ошибка прибора) и скопление
  видимости на отметке 2000 (25.6 % строк) — но это не подтверждённые
  дефекты, поэтому в baseline сохраняются без замены.
- **Целевая переменная.** Распределение правоскошенное (асимметрия ≈ 1.15),
  среднее выше медианы. 295 нулевых часов (3.37 %) полностью совпадают
  с `Functioning Day = No` — это закрытие сервиса, а не отсутствие спроса,
  поэтому нули не являются выбросами.
- **Корреляции.** Наибольшая связь с целевой — у `hour` и `temperature`
  (Phi-K ≈ 0.60). Сильная мультиколлинеарность между температурой и точкой
  росы (Пирсон 0.91, Phi-K 0.89).
- **Динамика спроса.** У будней два пика — утренний (~08:00) и вечерний
  (~18:00); у выходных и праздников выраженного утреннего пика нет,
  максимум в ~17:00. Спрос выше летом и ниже зимой.

### Анализ взаимосвязей и создание признаков

В EDA выдвинуты и описаны гипотезы о новых признаках:

- тип дня (`day_of_week`, `is_weekend`, `day_type`) вместо бинарного `holiday`;
- циклическое кодирование часа (`hour_sin` / `hour_cos`);
- расстояния до пиковых часов (`hour_dist_to_8`, `hour_dist_to_18`);
- флаги ненулевых осадков/радиации (`rainfall > 0`, `snowfall > 0`,
  `solar_radiation > 0`) и флаг `visibility == 2000`;
- замена подозрительных нулевых значений влажности расчётными
  по температуре и точке росы.

### Стратегия предобработки

Сохраняются все строки (включая нерабочие часы), оба температурных
признака, целевая в исходных единицах без преобразования. Для линейных
моделей — `StandardScaler` + one-hot кодирование категорий; для деревьев
(например, CatBoost) — нативная обработка категорий без масштабирования.
Сравнение экспериментов — на одинаковых временных фолдах.

## Методология и валидация

### Выбор метрик качества

**Основная метрика — RMSE** (root mean squared error).

Почему выбрана именно она:
- задача регрессии, целевая — целое число аренд за час;
- RMSE **квадратично штрафует крупные ошибки**. Для спроса на велосипеды
  это важно: промахи в часы пик (вечерний пик ~18:00) стоят дороже
  небольших отклонений в «тихие» часы, и бизнесу критичнее не промахнуться
  именно в них;
- метрика измеряется в тех же единицах, что и целевая (аренды за час),
  поэтому RMSE читается напрямую как средняя «цена» ошибки. Целевую
  не логируем, шкала сохраняется — интерпретация честная;
- распределение целевой правоскошенное, с редкими большими значениями —
  RMSE адекватно отражает такие хвосты.

**Вспомогательные метрики:**
- **MAE** — устойчива к выбросам; отношение RMSE/MAE показывает, насколько
  модель чувствительна к крупным промахам;
- **R²** — относительное качество модели по сравнению с константным
  прогнозом (средним), удобна для итогового отчёта. Не выбрана основной,
  т.к. чувствительна к выбросам и шкале и не выражается в единицах задачи.

### Схема кросс-валидации

Данные — **почасовой временной ряд** (один год), поэтому случайное
перемешивание дало бы утечку будущей информации в обучение. Используется
**хронологическое разбиение**:

- **train → validation → test = 70/15/15**, без `shuffle`. Test **заморожен**:
  используется один раз в конце для итоговой оценки, не участвует
  в отборе признаков и подборе гиперпараметров.
- **Внутри train — `TimeSeriesSplit(n_splits=4, gap=24)`**: каждый фолд
  обучается только на прошлом и валидируется на будущем. `gap=24`
  исключает 24 часа между обучающей и проверочной частями — защита
  от утечки из-за сильной автокорреляции соседних часов (спрос в час `h`
  тесно связан со спросом в час `h+1`).
- **Результат по фолдам — среднее и разброс (`mean ± std`)**, а не одна
  цифра: это показывает стабильность качества на разных временных
  интервалах (у спроса сильная сезонность, поэтому разброс между фолдами
  значим).
- **Утечек данных нет:** препроцессинг (масштабирование, one-hot
  кодирование) обучается только внутри обучающей части каждого фолда
  и применяется к валидации/тесту без пересчёта.

## Моделирование и оптимизация

Весь код — в модульном пайплайне `src/pipeline/`.

**Установка окружения:**

```bash
python3.12 -m venv .venv
.venv/bin/pip install -U pip
.venv/bin/pip install numpy pandas scikit-learn kagglehub \
    catboost xgboost lightgbm matplotlib seaborn phik statsmodels ipywidgets
```

**Запуск пайплайна:**

```bash
# из конфига (например, CatBoost)
.venv/bin/python -m src.pipeline.run --config configs/catboost.json

# без конфига — модель выбирается флагом
.venv/bin/python -m src.pipeline.run --model ridge
.venv/bin/python -m src.pipeline.run --model catboost --tune
```

### Baseline-модель

За baseline взяли **линейную регрессию с регуляризацией Ridge** — простую,
быструю и интерпретируемую. Для неё числовые признаки масштабируются
(`StandardScaler`), категориальные кодируются one-hot.

Признаки baseline:
- **базовые числовые:** `hour`, `temperature`, `humidity`, `wind_speed`,
  `visibility`, `dew_point_temp`, `solar_radiation`, `rainfall`, `snowfall`;
- **категориальные:** `seasons`, `holiday`, `functioning_day`;
- **добавленные временные:** `day_of_week`, `month`, `is_weekend`,
  `hour_sin`, `hour_cos`.

Метрики Ridge (`configs/ridge.json`):

| split | RMSE | MAE | R² |
|---|---:|---:|---:|
| train | 413.52 | 297.82 | 0.577 |
| val | 506.68 | 387.93 | 0.498 |

CV RMSE (train): **532.06 ± 215.94**.

### Техники улучшения на уровне данных: фичи вкл/выкл

Проверили, что дают добавленные временные признаки: обучили baseline
с ними (`configs/ridge.json`) и без них — только базовые признаки
(`configs/ridge_nofeatures.json`).

| Вариант | CV RMSE | val RMSE | val R² |
|---|---:|---:|---:|
| Без добавленных фич | 523.16 ± 227.64 | 509.52 | 0.492 |
| С добавленными фичами | 532.06 ± 215.94 | 506.68 | 0.498 |

**Вывод:** добавленные временные признаки дают небольшое улучшение на
валидации (val RMSE 509.52 → 506.68, ~0.6 %; R² 0.492 → 0.498). Разница
небольшая: линейная модель слабо использует циклические/временные признаки.
Существенно больший эффект они дают для деревьев и бустингов.

### Бустинг — следующий уровень моделей

Следующая по уровню модель — **градиентный бустинг**. Выбрали **CatBoost**:
он нативно работает с категориальными признаками без ручного кодирования
и лидировал в сравнении XGBoost/LightGBM/CatBoost. Метрики по умолчанию
(500 итераций, learning_rate 0.05, depth 6):

| split | RMSE | MAE | R² |
|---|---:|---:|---:|
| train | 119.79 | 73.94 | 0.965 |
| val | 284.33 | 198.41 | 0.842 |

CV RMSE: **352.96 ± 131.01**.

CatBoost значительно лучше baseline: val RMSE 284.33 против 506.68,
R² 0.842 против 0.498.

### Подбор гиперпараметров бустинга

Grid-поиск по сетке: `iterations ∈ {500, 800, 1200}`, `learning_rate ∈ {0.05, 0.1}`,
`depth ∈ {6, 8}` (`configs/catboost_grid.json`).

Лучшая комбинация: **iterations=800, learning_rate=0.05, depth=6**.

| Метрика | До (дефолт) | После (тюнинг) | Изменение |
|---|---:|---:|---:|
| CV RMSE | 352.96 | 352.69 | −0.27 |
| val RMSE | 284.33 | 282.82 | −1.51 |
| val MAE | 198.41 | 195.69 | −2.72 |
| val R² | 0.842 | 0.844 | +0.002 |

**Вывод:** дефолтные параметры уже близки к оптимальным; grid-поиск дал
небольшое улучшение за счёт увеличения числа итераций (500 → 800) при
той же скорости обучения и глубине. Более заметного выигрыша не получено —
модель и так сильная. Следующий шаг — байесовская оптимизация (Optuna)
с расширенным пространством поиска.
